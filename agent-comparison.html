⚡ 一句话总结

oh-my-pi：一个工程化程度极高的编码 Agent 框架，在上下文管理、安全防御、会话压缩方面做到了业界天花板级别，但它是 CLI-first 设计，缺乏终端深度集成。
waveterm：一个终端原生 AI 助手，在终端感知、交互检测、远程会话方面独树一帜，但 Agent 框架层的成熟度（上下文管理、压缩、安全）还有明显差距。

📐 架构设计差异详解

维度oh-my-piwaveterm
消息模型 AgentMessage 联合类型 (user/assistant/toolResult/aside/hook)，支持 Aside 消息注入（诊断、通知等不进入 LLM 上下文） GenAIMessage 接口，消息直接存入 chatstore，无 Aside 概念，所有消息都进入 LLM 上下文
上下文构建 Append-Only + StablePrefix：systemPrompt 和 tools 冻结后不再重序列化，最大化 provider prefix cache 命中率 每轮重建：SystemPrompt 数组每轮 append，TabState 每轮重新生成，无缓存优化
中断机制 interruptMode: "immediate" | "wait"，immediate 模式下每个工具调用后检查用户中断 无显式中断模式，依赖 SSE 连接断开 (ctx.Err()) 和用户取消审批
暂停续跑 支持 pause_turn (stopDetails.type === "pause_turn")，MAX_PAUSED_TURN_CONTINUATIONS = 8 限制无限续跑 无 pause 概念，stopReason 只区分 toolUse / error / done
事件系统 EventStream 事件驱动，支持 onAssistantMessage / onToolResult / onRunEnd 等细粒度事件 SSE 推送，前端被动接收 data-* 事件，无事件订阅机制
遥测 OpenTelemetry span 体系，chatSpan / executeToolSpan / invokeAgentSpan，覆盖率追踪 AIMetrics 简单计数 (RequestCount / ToolUseCount / ToolDetail map)
模型切换 invalidateForModelChange() 重置 prefix + log，支持运行中切换模型 Premium 限速时自动降级 (PremiumOpenAIModel → DefaultOpenAIModel)，其他场景不支持
关键差距：oh-my-pi 的 Append-Only 上下文管理是一个精妙的设计——它让 provider 的 prefix cache 最大化命中，每轮只有新增的 delta 是 cache miss。waveterm 每轮重建整个上下文，在长对话场景下 token 浪费严重。

📦 SnapCompact 压缩策略详解 (oh-my-pi 独有)

SnapCompact 压缩流程: ═══════════════════════════ 1. Token 阈值检测 └─ countTokens(messages) > threshold └─ 触发压缩 2. 策略选择 ├─ Short Summary → 简短对话摘要 ├─ Full Summary → 详细对话摘要 + 文件操作合并 ├─ Update Summary → 增量更新已有摘要 ├─ Turn Prefix → 保留最近 N 轮完整上下文 └─ Handoff Document → 跨会话交接文档 3. 文件操作合并 (FileOperations) ├─ extractFileOpsFromMessage() → 提取每个消息的文件操作 ├─ computeFileLists() → 计算最终文件状态 └─ upsertFileOperations() → 合并到摘要中 4. OpenAI Remote Compaction └─ 使用 OpenAI 的 remote compaction API └─ shouldUseOpenAiRemoteCompaction() └─ requestOpenAiRemoteCompaction() 5. 压缩后处理 └─ replaceTail() → 替换 AppendOnlyLog 尾部 └─ resetSyncCursor() → 重置同步游标
最大差距：上下文压缩是长对话 Agent 的命门。oh-my-pi 的 SnapCompact 做到了多策略、增量更新、文件操作合并、跨会话交接，而 waveterm 目前只有"用量警告"——当 token 接近上限时提示 LLM 注意，但没有实际压缩动作。这是 waveterm 最需要补课的地方。

🔬 Harmony Leak 检测详解 (oh-my-pi 独有)

Harmony Leak Detection — GPT-5 协议泄露防御 ═══════════════════════════════════════════════════ 5 信号融合检测: ┌─────────────────────────────────────────────────┐ │ M = MARKER_RE → to=functions.xxx 模式匹配 │ │ C = CHANNEL_WORD → channel + marker 邻接检测 │ │ G = GLITCH_RE → 故障 token 邻接检测 │ │ B = BODY_CASCADE → marker → code → marker 级联 │ │ R = FAKE_RESULT → marker + Cell N: 伪造结果框架 │ └─────────────────────────────────────────────────┘ 检测流程: detectHarmonyLeakInAssistantMessage(msg) ├─ 扫描 content 文本 → MARKER_RE 匹配 ├─ 扫描 toolCalls → 每个 call 的 input ├─ 信号融合 → signals[] 数组 └─ 信号数 ≥ 1 → 触发 HarmonyLeakInterruption 恢复策略: recoverHarmonyToolCall() ├─ 截断泄露内容 (removed = extractHarmonyRemoved) ├─ 恢复 edit 工具的 hashline DSL 输入 └─ 其他工具 → abort-and-retry 审计: createHarmonyAuditEvent() └─ 记录检测信号、截断内容、恢复结果
值得学习：Harmony Leak 检测是 oh-my-pi 针对 GPT-5 内部协议泄露的专项防御。虽然 waveterm 暂时不需要这个具体功能，但"LLM 输出安全检测"这个思路非常重要——Agent 不应该无条件信任 LLM 的输出。waveterm 至少应该加入：1) 工具参数异常检测 2) LLM 输出注入检测 3) 敏感信息泄露检测。

💡 向 oh-my-pi 取经：优先级排序

P0 上下文压缩 (SnapCompact)

现状：waveterm 只有用量警告，无实际压缩。
建议：实现多策略压缩——先做 Short Summary（简单摘要），再做 FileOperations 合并（文件操作去重），最后做 Handoff Document（跨会话交接）。这是长对话 Agent 的命门。

P0 Append-Only 上下文

现状：waveterm 每轮重建整个上下文。
建议：实现 StablePrefix + AppendOnlyLog——冻结 systemPrompt 和 tools，消息只追加不重序列化。这能大幅减少 token 浪费，提升 provider prefix cache 命中率。

P1 LLM 输出安全检测

现状：waveterm 无条件信任 LLM 输出。
建议：不需要照搬 Harmony 检测，但至少加入：1) 工具参数异常检测 2) Prompt Injection 检测 3) 敏感信息泄露检测。建立"不信任 LLM 输出"的安全意识。

P1 会话分支与快照

现状：waveterm 会话是线性的，无分支。
建议：实现 parentSession 分支机制——用户可以从任意点分叉出新会话，保留原会话状态。同时支持快照，方便回滚。

P2 中断与暂停机制

现状：waveterm 无显式中断模式。
建议：实现 interruptMode: "immediate" | "wait"——immediate 模式下每个工具调用后检查用户中断，wait 模式下等当前轮完成。同时支持 pause_turn 限制 (MAX_PAUSED_TURN_CONTINUATIONS)。

P2 OpenTelemetry 遥测

现状：waveterm 只有简单计数。
建议：引入 span 体系——chatSpan / executeToolSpan / invokeAgentSpan，支持分布式追踪和性能分析。这对调试复杂 Agent 行为非常有帮助。

保持 终端感知优势

现状：waveterm 的终端感知是核心差异。
建议：继续深耕——增强 TUI 检测（支持更多 TUI 程序）、改进交互检测（支持更复杂的提示模式）、优化远程会话路由（支持跳板机）。

保持 车道化并行执行

现状：waveterm 的三车道执行计划是务实设计。
建议：oh-my-pi 完全依赖 LLM 决定并行性，容易出问题。waveterm 的车道化方案更安全，值得保持和增强——比如加入依赖声明，让工具可以声明前置依赖。
